# 下一项目提案：交件 Agent

日期：2026-10-22。状态：调研与设计，尚未实现，尚未验证用户收益或付费需求。本文不是轻迁的新功能，也不是一个已经上线的 Agent。

## 1. 先限定一个实际任务

面向需要向多个目标重复提交申请材料的人，先选择材料较多、要求有条件分支的高校申请场景。用户已经有一份正式材料要求和一组 PDF、照片；目标是完成要求核对、材料整理并得到可供最终复核的提交文件。

典型麻烦不是“忘了记录自己有什么”，而是不同目标要求不同：材料范围、提交顺序、文件命名、合并与拆分方式、大小限制都可能变化。Agent 应承担其中可以执行和验收的处理工作。

## 3. 用户需要付出什么

提供正式通知的文字或 PDF，再选择已有的材料文件。第一版只支持 PDF、JPG、PNG，限制单次任务规模。若通知存在互斥分支，只询问决定分支的少量事实；若自动匹配不确定，只请用户处理对应文件。

不要求事先建立材料管理台账。首次设置、文件选择、模型等待、纠错和最终核对的耗时全部计入工具成本。如果用户仍须逐份重新登记、分类和检查，便重现了轻迁的问题。

## 4. Agent 真正交付什么

1. 读取通知，提取材料条目、适用条件、顺序、命名和大小规则；每条保存原文位置，规则缺失就标记未知。
2. 检查已选文件的类型、页数、字节大小和可读取内容，提出材料匹配候选。存在多个版本、缺件或无法读取时列出具体问题。
3. 根据当前任务选择下一步工具：直接复制、图片转 PDF、按顺序合并，或在不牺牲必要可读性的前提下尝试大小优化。
4. 重新打开输出，检查能否读取、文件名、页数、顺序映射和字节大小。未达标时修改计划或明确报告失败，禁止用一句“已处理”代替实际验收。
5. 交付生成的文件、原文规则与文件映射表，以及“已检查／待人工核对／未满足”的报告。原件保留。

材料存在缺项时，可以提供已有部分的草稿包，但必须明确显示缺项；不能把不完整的结果标为完成。最终提交由用户自行决定。

## 5. 为什么需要 Agent，以及什么时候不需要

待验证的 Agent 工作是根据要求和工具反馈改变处理计划：先确认适用分支，遇到未知文件再检查内容，发现输出超限再选择可行的处理方式，最后根据真实文件检查结果决定交付状态。

模型主要理解自然语言要求、处理歧义和选择工具；文件是否存在、名称是否匹配、实际大小和输出能否打开，由确定性程序核验。模型不能凭空宣告通过。

如果任务仅为固定顺序的两三个 PDF 合并，使用现有 PDF 工具即可。如果所有场景都能被简单规则稳定覆盖，应做普通工具，不应为了简历强行增加 Agent。

## 6. 首版实现范围与接入成本

先用一个简单网页配合小型本地服务验证真实处理流程：网页选择已有文件，服务在任务临时目录中读取和生成副本，完成后下载成品与报告。模型服务单独配置，真实模型调用失败必须显示失败；规则回退不能冒充模型推理。无需 Scalar 或复杂 Agent 平台。

这一方式能真正读写和验证文件，但启动本地服务、配置模型也会增加使用成本，必须纳入对照测试。公开静态网页可展示脱敏样例；不能把 GitHub Pages 演示声称为已经提供了后端 Agent。若以后提供托管版，再单独解决后端运行、数据存储、模型费用和用户授权。

任务文件不发布到仓库。远程模型调用应优先只使用公开要求和去除个人身份信息的文件元数据；真实材料正文若确实需要外发，必须说明发送范围并取得用户同意，不能声称默认全本地。扫描件无法提取文本时应使用已实现的 OCR 或交由人工核对，不能假装已读懂。[pypdf 官方限制说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)

普通网页直接改动用户文件系统存在授权和兼容限制，因此首版使用显式文件选择和副本输出，不承诺后台接管下载目录。[Chrome 文件系统文档](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)

## 7. 明确不承担的判断

材料格式与准备情况检查不等于申请资格审查，也不证明材料真实性、签章有效性或最终被接收。对于这些要求，只提示需要人工核对及其原文依据。

数字签名文件的合并或重写可能影响验证，应识别并提示处理边界；无法可靠处理的文件保留原样、报告阻碍。压缩不能保证任意 PDF 都达到指定大小；不能通过删去必需页面或使文字不可读来换取“达标”。

## 8. 开发前写清验收与淘汰条件

以下都是待执行的验收标准，没有声称已经通过：

- 只给原文要求与已有文件即可开始。所有输出规则可回到来源；条件缺失时问具体问题，不猜测适用分支。
- 使用人工标注的正常、缺件、多版本、不可读、加密和超限样例，检查系统是否正确区分已满足、未满足与未知；尤其不能把有缺项的任务误报完成。
- 成品实际可打开，文件名、页数、页序和字节大小符合已经确认的要求；失败必须保留明确状态和原因。
- 输入文件处理前后哈希一致，重跑、取消及工具异常都不覆盖原件或把残缺输出标成完成。
- 用同一批任务对照用户现有做法，记录完整用时、人工纠错次数、遗漏和最终文件质量；把安装、模型配置与核对都计入，不能只比较程序运行时间。

先找有真实多目标申请任务的用户自愿试用，在明确授权下使用其现有文件，或用保持复杂度的脱敏副本。若复核 Agent 的成本抵消了处理收益、关键缺项无法可靠暴露，或用户只需要简单合并，则缩小范围或淘汰该方向。

## 9. 当前业务判断

这是值得先做小范围任务验证的候选，比让用户新增物品登记更贴近一项原本就必须完成的工作。它仍有申请季集中、用户不愿提供材料、机构模板差异和错误后果等限制。

现阶段不编造套餐价格、订阅留存、用户规模或付费数据。先验证实际减少操作与返工，再决定它适合作为个人工具、免费项目还是可收费服务。
