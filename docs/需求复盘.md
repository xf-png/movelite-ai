# 轻迁 MoveLite：需求复盘

日期：2026-10-22。状态：可运行的技术演示，消费需求尚未验证。

## 这次选题遗漏了什么

此前围绕容量、时间和费用设计了完整流程，却没有先比较用户的现有做法。用户给出的具体反馈是：整理时就可以决定哪些丢、哪些留，没有必要先在平台登记。

这直接挑战了核心前提。使用轻迁需要先登记物品、估算体积、处置时间和转让金额；其中部分信息平时并不存在，还需要人为估计。用户承担的准备成本可能高于方案带来的帮助。AI 分类和组合求解即使能正常运行，也不能证明使用整个产品更省事。

这是一次具体使用场景反馈，不是大样本调查。但它已经足以说明，现有材料无法支持“消费者会为此付费”的判断。

## 工程结果与产品结果分别记录

- 已完成：可运行网页、本地语义分类、容量与时间约束求解、锁定与不可行提示、记录和导出，以及已列明的技术检查。
- 尚未证明：用户愿意完成登记、方案比现场决定更有帮助、总耗时减少、愿意支付费用。
- 原先的 ¥9.9 / ¥19.9 仅为未验证的候选价格，没有收款或真实购买数据。

项目保留源码、测试和在线演示，作为工程学习与简历展示材料。简历应写实际实现，不能把技术检查通过写成产品需求成立。

## 下一次选题要先回答的问题

1. 用户原本必须完成什么任务？现在怎么完成，真正费时的是哪一步？
2. 所需数据是否已经存在？提供截图、文件或链接的成本是否明显低于手动完成？
3. 完成后能交付什么可检查的结果？例如一个实际可用的文件包，而不只是建议文字。
4. 简单规则、系统功能、现有软件或一次普通 AI 对话能否解决？如果可以，为什么还需要 Agent？
5. Agent 是否确实需要根据工具结果选择下一步，并验证执行结果？固定流程不能仅因调用模型就称为自主 Agent。
6. 真实使用中需要多少人工纠错？把授权、安装、模型等待和核对时间全部计入成本。
7. 什么结果会让我们放弃这个方向？验证门槛必须在开发前写明。

## 后续验证方式

先用用户已有的任务和文件做小范围对照，分别记录手动完成与工具完成的总耗时、错误、返工和实际交付结果。只有当工具在这些具体任务上提供帮助，才扩大实现范围。便利性、准确率、收益和付费意愿分别测量，不互相替代。

新 Agent 的 [选题提案](下一项目提案-交件Agent.md) 已单独标为调研与设计阶段，避免将研究方案与已经实现的轻迁功能混淆。它建议先验证材料预检与打包任务，并写明原文依据、输入成本、验收与淘汰条件。
